## 1. Term-pair interleaved w′ value table

**Mechanism.**
- **Today:** TABLE_W's value table G is q-major, `[pairs × pieces, Q = 1280, 6]` (`value_table`,
  `wprime_backward.py:642`). Each lane reads its weight's six terms as three `float2` (`gq + k`, template
  near line 293).
- **The waste:** lanes hold consecutive q, so their rows are 24 B apart.
  - One warp-wide `LDG.64` returns 256 useful bytes spread over 768 B. That is six 128-byte lines, and so six
    L1 wavefronts if one wavefront is counted per line, the usual L1TEX accounting.
  - The three loads of a weight walk the same six lines again: 18 wavefronts where 6 carry the data.
- **The change:** store G as `[pairs × pieces, 3, Q, 2]` (term pair, then q). Lane l's k-th `float2` then
  sits at `(k·Q + q)·2`, and a warp's load is 256 contiguous bytes, two wavefronts. The values, the
  registers they land in and the Horner order stay the same.
- **Variant B:** a `[Q, 4]` plane plus a `[Q, 2]` plane, read as one `LDG.128` and one `LDG.64` per weight.
  That is two load instructions instead of three, and 4 + 2 wavefronts.

**Attacks.** The w′ is 1,606 µs, 28 % of the kernel time at `02a81e13`.

L1 wavefronts per edge-warp under the one-per-line model:

| Access | Wavefronts per edge-warp |
| --- | ---: |
| Table: 10 paths × 4 channel passes × 18 | 720 |
| dout (coalesced `LDG.32`) | 160 |
| x | 16 |
| sh (broadcast) | ≤ 64 |
| dx atomics | 16 |
| **Total** | **≈ 950** |

- **Today:** ≈ 950 wavefronts per edge-warp over 373,760 edges and 132 SMs is 2.7 M wavefronts per SM. The
  kernel lasts 3.18 M cycles per SM (1,606 µs at 1.98 GHz), so the L1 data path (128 B per cycle) would be
  about 85 % busy, three quarters of it on table lines fetched three times.
- **After the change:** ≈ 470 per edge (1.33 M per SM, 42 %).

**Evidence so far.**
- **RTX 5060 Ti:** the q-major `float2` table (`B-gslab-f2`, 0.744) beat a term-major table read with scalar
  loads (`B-gslab`, 1.047–1.055). Fewer load instructions won there.
- **The interleave:** it keeps `B-gslab-f2`'s instruction count (variant B lowers it) and has `B-gslab`'s
  coalescing, so on paper it beats both.
- **Ada:**
  - without the table, 0.599;
  - with every edge reading one slab, 0.751, so a table that only hits L1 still cost ≈ 15 %.
- **H200:**
  - one slab gives only 0.925, so little of the table's cost there is L2 or HBM misses;
  - the rest is on the L1 side (one slab leaves the wavefronts unchanged) or in instruction issue.

**Ceiling.**
- **Upper bound:** if the w′ is bound by L1 wavefronts, removing 480 per edge frees ≈ 1.36 M cycles per SM
  (0.69 ms). The kernel's instruction issue then sets the limit; my rough estimate is ≈ 1.0 ms at full issue,
  to be replaced by the SASS count. Ceiling ≈ −0.6 ms (−10 % of the step).
- **Expected:** −0.1 to −0.4 ms.
- **Void case:** if ncu shows the table requests already at ≈ 2 wavefronts each, the model is wrong and the
  idea is void.

**Exactness.** Bitwise. The table is built once in float64 and only permuted, and the loads fill the same
registers.

**Falsifier.**
1. **Lab variants** in `tools/omat0_kernel_lab.py`, next to `B-gslab-f2` (line 474):
   - `B-gslab-pair`:
     - **Arguments:** `g.view(P, Q, T // 2, 2).permute(0, 2, 1, 3).contiguous()`.
     - **Source:** `reinterpret_cast<const float2*>(g + weight_index * PADDED_TERMS)` … `__ldg(gq + k)`
       becomes `reinterpret_cast<const float2*>(g) + weight_index` … `__ldg(gq + k * WEIGHT_DIM)`.
     - **Check:** assert the outputs are bitwise equal to the base.
   - `B-gslab-42`: the same for variant B.
2. **ncu on the base w′:**
   - `l1tex__data_pipe_lsu_wavefronts_mem_lg_cmd_read.sum` per `l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum`;
   - the stall reasons `lg_throttle`, `mio_throttle` and `long_scoreboard`.

Keep the idea if the lab ratio is ≤ 0.97.

**Effort.** Half a day:
- a layout flag in `value_table`;
- the template address;
- the lab variant;
- a GPU test that checks the result bitwise against q-major.

Every reader of G must follow the layout; check the rebuild backward, which refused SLOPE_VECTOR. The change is
bitwise, so it is likely useful on every GPU, each after its own step A/Bs (decision 66).

## 2. Degree-pure path parts in the fused forward

**Mechanism.**
- **Today:** `balanced_parts` (`fused_forward.py:677`) splits the ten paths into two parts of five by
  angular-term cost:
  - part 0 = (0,0,0), (0,1,1), (1,2,1), (1,3,2), (0,3,3);
  - part 1 = (0,2,2), (1,0,1), (1,1,0), (1,1,2), (1,2,3).
- **The waste:** both parts mix l1 = 0 and l1 = 1 paths. Each part therefore loads all four x rows of every
  sender (x0 and the three x1 components): eight row gathers per edge and channel block.
- **The change:** split by input degree:
  - part A = the four scalar-input paths, which need only x0;
  - part B = the six vector-input paths, which need only x1.

  That is four gathers instead of eight.

**Attacks.** F-no-xload measured 1,928.8 µs against 2,323.4 µs (0.830) at `27d27f21`, so the x gathers cost
≈ 395 µs. Neither SKIP_ZERO_COLUMN nor VEC_A changes them, so I assume the same cost at `02a81e13`; the bound
has not been rerun there.

**Ceiling.**
- **Upper bound:** half of 395 µs is −197 µs: 11 % of the 1,786 µs forward at `02a81e13`, 3.4 % of the step.
  This assumes the cost scales with the number of row gathers.
- **Expected:** −80 to −150 µs, because every edge still waits for one gather per part.

**Fit.**
- **Shared memory:** part B needs the larger W slice:
  - the W slice in fragment order: 6 paths × 8 × 2 × 32 × 4 floats = 49.2 KB at K = 64;
  - staging: 12 warps × (8 × (64 + 16) + 6 × 8 × 36) floats = 113.7 KB.

  The total is 162,816 B of the 232,448 B (227 KiB) a block may use; today's forward uses 151,040 B.
- **Registers:**
  - 12 m-tiles × 4 accumulators = 48 (40 today);
  - x values: 3 × 8 = 24 (32 today).

  The peak stays the same.
- **Phase balance:** the two part phases run one after the other, since only one 160 KB block fits per SM.
  Only their sum counts, so the uneven split (8 against 12 m-tiles) costs nothing.
- **Other GPUs:** on the A100 (163 KB) the fit is borderline; on the RTX 5060 Ti (99 KB) it needs fewer warps.
  It would be a default for the H200 (and H100) under decision 66.

**Exactness.** Bitwise: each output slot keeps its terms and its edge order.

**Falsifier.**
- **The switch:** a constants-hook switch `PARTS_BY_INPUT_DEGREE` where `launch_rule` forms the groups,
  scalar- or vector-input by `paths[i].input_irrep_dim`. `slice_floats` and `staging_floats` take the larger
  part.
- **The lab variant:** `F-pure-parts`, bitwise against the base. ptxas must report ≤ 168 registers and no new
  spills.
- **Both product paths:** generate it for `_part` and the new `_part_wgmma`. Part B's wgmma N becomes
  6 × 32 = 192, which is legal.

**Effort.** Half a day to a day.

## 3. Piece-sorted radial-table evaluation

**Mechanism.**
- **Today:** `radial_table_forward` computes for each edge a = Σ_k T_k(t) C[pair, piece, k, :]. Each edge reads
  6 terms × 66 columns of coefficients, 1,584 B. The edges run in receiver order, so the 32 edges of a block
  hit 32 unrelated (pair, piece) rows, and every edge reads its 1.6 KB from L2. That is 592 MB per call, out
  of a table of only 8.9 MB (624 pieces) or 12.8 MB (896 pieces).
- **The change:**
  1. Sort the edges each step by a 16-bit key: symmetric pair × 4096 + r quantised to 12 bits.
  2. Evaluate in that order, so neighbouring edges share rows through L1.
  3. Store each row to `a[perm[e]]`, 260 contiguous bytes per edge, so the consumers keep receiver order.

  Both tables are monotone in r, so one sort serves both calls.

**Attacks.**
- **The table kernels:** `radial_table_forward` takes 115.0 + 114.7 µs.
  - 592 MB per call in 115 µs is 5.1 TB/s of L2 reads, the order of Hopper's L2 bandwidth.
  - The output writes are only 97 MB, ≈ 20 µs at 4.8 TB/s.
- **Extension:** interaction 1's `tabled_outer_sum_backward` (239.7 µs) gathers the 896-piece derivative rows
  the same way: 5 × 66 × 4 B = 1,320 B per edge, 493 MB per call.
  - The sorted forward could store da/dr [E, 64] beside a. That costs 96 MB of writes, then one contiguous
    read.
  - It saves a further ≈ 50 µs if that kernel is L2-bound.

**Ceiling.**
- **Upper bound:** each call drops to ≈ 30 µs (writes and compute), −170 µs in all. The sort costs
  ≈ 15–25 µs: a CUB radix sort of 373,760 16-bit keys with 4-byte values, in two 8-bit passes. The net
  ceiling is ≈ −150 µs (2.6 %).
- **Expected:** −60 to −120 µs.
- **If TABLED_FORWARD becomes the H200 default:** interaction 1's table is then evaluated inside the
  outer-sum kernel, in receiver order. This idea then covers interaction 2's call only, net ≈ −65 µs. The
  capture fix `0017749a` makes that A/B possible now.
- **Sorting only at rebuilds** (every ≈ 8 steps) is cheaper but drifts:
  - at 300 K edges move ≈ 0.08 Å in 8 steps, ±9 pieces of 0.009 Å;
  - a block then still touches ≈ 18 rows, only ≈ 45 % less traffic.

**Exactness.** Bitwise: each edge runs the same code on the same row; only the order changes.

**Falsifier.**
1. **ncu on the base kernel:** `lts__t_sectors_srcunit_tex_op_read.sum` and the L2 throughput in % of peak.
   Drop the idea below 60 % of peak.
2. **Lab:**
   - sort in the harness (`perm = torch.argsort(key)`);
   - run the kernel on `r[perm]` and `pair[perm]`;
   - scatter the result back;
   - time the kernel and the sort separately.

   Keep the idea if (kernel + sort) / base ≤ 0.7.

**Effort.** One to two days:
- an int16 key kernel and `torch.sort` or CUB in the graph;
- a perm-aware store and the backward's matching gather;
- tests.

## 4. S tile: CG·sh once per edge instead of once per lane

**Mechanism.**
- **Today:** the generated TP (`_part`, `fused_forward.py:1415`; `_part_wgmma`, line 1122) computes each
  output component as `acc = fmaf(w, xv*e*coef + …, acc)`, one channel per lane.
- **The waste:** the product e × coef does not depend on the channel, yet all 32 lanes recompute it. That is
  about two instructions (FMUL + FFMA) per Clebsch–Gordan term per edge and lane.
- **The change:**
  1. Compute per edge S[m1][m3] = Σ_{m2} CG[m1,m2,m3] e[m2] once per warp:
     - 82 values for OMAT-0's ten paths: 66 for the vector-input paths, 16 for the scalar ones;
     - ≈ 2.6 values per lane per edge.
  2. Store them in the `r_s` tile after the w read-back, or in a 2.6 KB per-warp tile from the spare shared
     memory.
  3. Each lane then computes Σ_{m1} S[m1][m3] x[m1], reading S with broadcast `LDS.128`.

Instructions per edge and lane for the ten paths, counted from the generator's terms:

| Work | Today | With S |
| --- | ---: | ---: |
| Angular terms: FMUL + FFMA per CG term (92 terms) | ≈ 184 | — |
| S·x on the vector-input paths (66 FFMA) | — | 66 |
| Scalar-input paths (4 FMUL + 16 FFMA) | — | 20 |
| `fmaf(w, …)` per output component | 40 | 24 |
| Shared-memory reads (sh today, S with the tile) | ≈ 16 | ≈ 21 (`LDS.128`) |
| Share of building S | — | ≈ 8 |
| **Total** | **≈ 240** | **≈ 140** |

That is about 40 % fewer.

**Attacks.** F-no-tp measured 0.669 (−769 µs at `27d27f21`), which includes the x gathers (−395 µs). The TP
arithmetic itself is therefore ≈ 370 µs.

**Ceiling.**
- **Upper bound:** −40 % of 370 µs ≈ −150 µs (8 % of the forward, 2.6 % of the step), if the TP is
  issue-bound.
- **Expected:** −60 to −120 µs, because the TP overlaps the product and the loads.

**Precedent.** The rejected TC_TP (omat0-tc-tp; A100 lab 1.276, RTX 5060 Ti 1.64) built the same
S[m1][m3] = Σ_{m2} CG[m1,m2,m3] e[m2], but fed it to a second 3xTF32 mma. It lost because preparing each A
element (the multiply by x and the 3xTF32 split of both operands) cost about as much as the FP32 terms it
replaced. The S tile keeps the FP32 SIMT TP and drops only the per-lane recomputation of CG·e, so it has none
of that preparation.

**Exactness.** Not bitwise: (Σ CG e) x replaces Σ (x e) CG. The difference is at float32 rounding level and
needs the force/stress gate. For scale: TC_TP's message, with the same pre-summed S and a 3xTF32 TP on top,
was within 4–6e-7 rms of the FP32 TP.

**Falsifier.**
1. **SASS census, no GPU needed:**
   - compile the generated source (the lab writes it) with NVRTC for sm_90; NVRTC needs no device;
   - run `cuobjdump -sass`;
   - count FMUL and FFMA inside the batch loop's TP block.
2. **Lab variant:** build `F-stile` only if FMUL is close to the number of terms.

The idea combines with idea 2: part B holds all the vector-input paths.

**Effort.** One to two days:
- the S generator per part and the lane assignment;
- `__syncwarp`;
- both product paths.

## 5. Small exact tail cuts

**Mechanism.** Three cuts:
- **(a) Edge adds:** after `tabled_outer_sum_backward` (interaction 1, sequence index 155 in
  `kernel_sequence.csv`), three `aten::add_` kernels at 156, 157 and 159 add its edge gradients into
  interaction 2's. The `[373760, 16]` one takes 16.4 µs. If interaction 1's backward adds into those buffers
  in its epilogue (load, add, store: the same IEEE add), the three kernels go.
- **(b) Density sums:** the forward's two density `scatter_add`s take 18.4 and 19.5 µs (indices 34 and 63; a
  `[2, E]` index and `[E, 1]` values into `[5000, 1]`).
  - Today they are atomics onto 5,000 addresses with ≈ 75 edges each.
  - Because edges are receiver-sorted, a segmented sum in the kernel that produces the value does the same
    work: block-local, with two atomics per block at the segment ends.
  - Index 12 (26.8 µs, envelope and scatter) may be the same pattern.
- **(c) One-hot embedding:** the species embedding is an FP32 cuBLAS `aten::mm` of `[5000, 89] × [89, 128]`
  (8.2 µs) on one-hot rows. A row gather gives the identical result: the sum of exact zeros plus 1 × w is w.

**Ceiling.** ≈ −20 µs (a) + ≈ −38 µs (b) + ≈ −6 µs (c) ≈ −65 µs (1 %).

**Exactness.**
- (a) and (c): bitwise.
- (b): the summation order changes, at rounding level. Today's atomics are unordered too.

**Falsifier.**
- **(b):** first name the producer of the two scattered values from Inductor's generated code
  (`TORCH_LOGS=output_code`). If it is our radial-table kernel's density column, prototype the segmented sum
  in the lab.
- **(a):** the adds come from gradient accumulation of tensors that both interactions use. Fusing them needs
  one custom op whose backward receives both gradients.
- **(c):** check that `node_attrs` is exactly one-hot.

**Effort.**
- (c): an hour;
- (b): a day;
- (a): one to two days of autograd plumbing.

## 6. One grouped launch per BlockLinear

**Mechanism.**
- **Today:** every BlockLinear launches its per-l products one by one.
  - Forward: M = 5,000, 15,000, 25,000 and 35,000 rows (l = 0 to 3) at N = 128; input gradients at
    N = 128–384.
  - An l = 0 product has 79 × 2 = 158 tiles of 64 × 64 for 132 SMs. It runs alone and is latency-bound.
- **The change:** one grouped launch per BlockLinear:
  - CUTLASS 2.x `GemmGrouped` with its problem visitor and the same 3xTF32 mainloop, so every element's sum
    is unchanged;
  - tiles ordered largest product first, so the small products hide under the large ones;
  - an N-fastest raster that also keeps a row tile's two column tiles together.

**Attacks.** fm_tf32x3 takes 865.8 µs in 37 launches.
- A single l = 0 launch (the lone `[79, 2]` calls) takes 7.3–7.6 µs for 0.16 GFLOP, 22 TFLOPS of useful
  FLOPs.
- The interaction-2 forward graph runs seven launches in 167.2 µs. Its six identified products (linear_up
  l = 0, 1 and the message linear l = 0–3) are ≈ 7.2 GFLOP, so ≥ 43 TFLOPS.

**Ceiling.**
- **Upper bound:**
  - at 43 TFLOPS an l = 0 product with K = 128 needs ≈ 3.8 µs, so ≈ 3.5 µs of each small launch is latency
    and tail;
  - about 11 such products per force call give ≈ −40 µs;
  - the l = 1 products add ≈ −10 to −20 µs.

  That is ≈ −60 µs (1 %).
- **Expected:** −20 to −50 µs.

**Exactness.** Bitwise: the same mainloop and the same K order.

**Precedent.**
- **lin-concurrent-branches:** the same overlap with streams inside the graph was rejected (murphy
  0.85–1.11×, local 0.68–0.98×).
- **grouped_launch:** it exists for Triton but is off beside `tf32x3_gemms`.
- **What is new:** a single grouped kernel avoids the stream fork/join and its scheduling noise.
- **With the wgmma bench (`10656ce3`):** this idea complements it; whichever mainloop wins can be launched
  grouped.

**Falsifier.** A CUDA-graph micro-benchmark on the recorded shapes (`tools/bench/gemm_shapes.py`):
- the four products of the interaction-2 message linear launched one by one;
- against one launch over a concatenated tile list.

A cheap bound comes from the existing Triton grouped kernel. Keep the idea at ≥ 15 µs per force call.

**Effort.** One to two days:
- a grouped instantiation in the sm_80 and sm_90 cubins;
- problem arrays in device memory, static per model.

## 7. 1-D bulk copies for the forward's a and sh staging

**Mechanism.**
- **The data:** a batch's eight a rows are one contiguous 2,176 B block, because a warp's edges are
  consecutive and the rows are stored padded to AS = 68 floats. Its eight sh rows are 512 B.
- **The copies:**
  - one lane issues `cp.async.bulk.shared::cluster.global.mbarrier::complete_tx::bytes` for each of the two
    blocks; a plain CTA counts as a cluster of one, so there is no tensor map and no multicast;
  - the warp waits on an `mbarrier` phase;
  - the next batch's copies go out before this batch's product.

  This gives double buffering without per-element registers, address arithmetic or `STS`.
- **No swizzle needed:** a lands with row stride 68 = KP + 4 floats. The fragment reads (`gid` 0–7, `tq` 0–3)
  then hit 32 different banks, as VEC_A's XOR swizzle does today. The same values reach the same mma.
- **Not the rejected prefetch:** PREFETCH (omat0-ff-prefetch) double-buffered the same rows with 4-byte
  `cp.async` and lost on the A100 (lab 1.071 / 1.038; re-screen 1.255). There the second buffer cost warps or
  spills at 168 registers and 12 warps. On the H200 both buffers fit: about 33 KB more than today's 151,040 B,
  within 232,448 B. Two bulk copies per batch need no per-element address registers.
- **Not the excluded staging:** this is per warp and per CTA, with no cluster launch and no multicast. Nor is
  it a producer/consumer split (the H200 microbench lost 1.1–1.5×): the warp that computes a batch issues the
  next batch's copies itself.

**Attacks.** What the `float4` staging of a and sh still costs.
- **The scalar staging's bound:** F-no-aload measured 0.864 in `F/` (2,009.4 against 2,324.9 µs at
  `27d27f21`). That kernel still read 65 columns with scalar loads, so they cost ≈ 316 µs.
- **What VEC_A took:** VEC_A alone is worth 4.7 % of the H200 step (b/a 1.047 / 1.046), ≈ 270 µs.
- **What is left:** ≈ 50 µs for a by subtraction. The two numbers come from different bases (kernel against
  step, 65 against 64 columns), so this is a rough guess. sh has no H200 bound, because F-no-shload failed on
  its stale pattern.
- **On the A100:** the vector staging (VEC_A + VEC_SH) gained 1.9–2.7 % of the step, and 3.0–4.6 % together
  with TC_WFRAG.

**Ceiling.**
- **Upper bound:** the repaired F-no-aload + F-no-shload bound against the `02a81e13` base. I estimate
  ≈ −60 µs: ≈ 50 µs for a, and a smaller share for sh, which has a quarter of a's bytes.
- **Expected:** 0 to −40 µs.

**Exactness.** Bitwise.

**Falsifier.** Repair the two bounds for the `float4` lines and run them against the `02a81e13` base:
- F-no-aload (`tools/omat0_kernel_lab.py:1051`): replace
  `__ldg(reinterpret_cast<const float4*>(a + (e0 + b) * AS) + q)` with `make_float4(0.5f, 0.5f, 0.5f, 0.5f)`;
- F-no-shload (`:1054`): the same for `__ldg(reinterpret_cast<const float4*>(sh + e0 * ED) + i)`.

Build only if together they give ≤ 0.95.

**Effort.** One to two days:
- an mbarrier pair per warp and its phase bits;
- the fragment reads at row stride 68 instead of the swizzle;
- tail batches with fewer than 8 edges: copy nb rows (multiples of 16 B) and zero-fill the rest, as today;
- both product paths.

## 8. PDL between adjacent kernels of our own

**Mechanism.**
- **Which kernels:** our own kernels (the NVRTC forward and w′, the CUTLASS GEMMs, the Triton tables) launch
  with `cudaLaunchAttributeProgrammaticStreamSerialization` where the previous kernel is also ours.
- **The secondary:** it runs its predecessor-independent prologue (the forward's W-slice fill; the GEMM's
  weight tiles and address setup), then `griddepcontrol.wait`.
- **The primary:** it signals `griddepcontrol.launch_dependents` once its last wave has started.
- **Unlike the rejected launch-pdl:** that one ran on Inductor's kernels and gave wrong forces. Here only
  kernels whose code we control take part.

**Attacks.**
- the 74 µs of gaps inside the replay over 166 launches;
- the overlap of each next prologue with a last partial wave.

Adjacent own-to-own pairs in the sequence include:
- the four GEMMs at 122–125;
- the radial-table backward → GEMM → fill → w′ at 126–129;
- the GEMM pairs at 132–133 and 152–153.

**Ceiling.** ≈ 1 µs per own-to-own boundary × ≈ 25–40 boundaries: −25 to −40 µs (≤ 0.7 %).

**Exactness.** Bitwise, if every read of a predecessor's output follows the wait.

**Falsifier.** An upper bound first: a captured graph of the four consecutive GEMMs, with the attribute set and
no wait (unsafe, timing only), against the same graph without it. Drop the idea below 3 µs.

**Effort.** One day plus a CUTLASS cubin rebuild, to put the wait in the kernel entry.

## 9. Hoist the piece scale out of the w′ slope

**Mechanism.** For each path and channel the w′ does `slope = radial_dt * sc; radial_gradient +=
weight_gradient * slope`, where `sc` is the piece's scale and the same for the whole edge. Instead, accumulate
`weight_gradient * radial_dt` and multiply the edge's sum by `sc` once. That saves 40 FMUL per lane and edge.

**Ceiling.** 373,760 edges × 40 warp instructions at one per cycle per scheduler is ≈ 14 µs of issue.
Expected −15 to −25 µs.

**Exactness.** Only dr changes, at rounding level (sc · Σ instead of Σ sc ·). dx and dsh stay bitwise.

**Falsifier.** A lab variant: `_sub(s, "slope = radial_dt * sc;", "slope = radial_dt;")`, plus
`radial_gradient *= sc` before the reduction.

**Effort.** An hour; bundle it with idea 1's lab job.

## Considered and dropped

- **Pre-split W in fragment order.**
  - Measured: TC_PRESPLIT 1.297 on the H200.
  - Reason: the hi and lo planes double the W slice's shared-memory traffic.
- **Changing the w′'s lane-to-channel ownership to pairs or quads**, for wider loads and sm_90's
  `red.global.add.v4.f32`.
  - Measured: the channel-pair variant ran 1.126 in the H200 sweep (0.898 on Ada, at 128 registers; at
    128 registers the H200 fits 16 instead of 20 warps per SM). Quads need more registers.
    F-no-atomics (1.089) shows the atomics are not the limit.
  - Reason: idea 1 gets the coalescing without touching ownership.
- **A dout locality walk.**
  - Measured: BACKWARD_WALK b/a 1.000 on the H200.
- **Radial tables on a side stream beside interaction 1's atom chain.**
  - Measured: launch-two-streams (0.985–1.151×) and lin-concurrent-branches were rejected.
  - Reason: it is the same overlap mechanism.
  - Re-probe it only if the H200 timeline shows interaction 1's atom chain below 50 % SM occupancy.
- **Mirror-edge sharing of the a·W product.**
  - Reason: edge and mirror sit in different receivers' warps. Sharing needs either w stored for half the
    edges (`[E/2, 1280]`, 0.96 GB) or atomics for the mirror's whole message (5,120 floats per edge).
  - Ledger: rad-mirror-edge was not built.
- **DMMA float64 tensor cores.**
  - Reason: 66.9 TFLOPS against ≈ 165 effective for 3xTF32.
- **Radial tables evaluated inside the fused forward.**
  - Reason: eight blocks restage each edge, 8 × 1.6 KB per edge ≈ 4.7 GB of L2 reads per call. This is the
    same failure as omat0-table-in-forward.
- **Running the w′ in (pair, piece) order.**
  - Reason: the table reads become local, but dout (20 KB per edge, 102 MB in all) becomes random.
  - Measured: one slab (0.925) caps the gain from table locality at 7.5 %.
- **An S tile in the w′'s FACTORED sums.**
  - Reason: u = Sᵀg saves only the u FMAs; v keeps the CG form, ≈ 228 → ≈ 218 instructions.
- **Split-K or stream-K for the small GEMMs.**
  - Ledger: lin-split-k was rejected.
  - Reason: it also changes the sums.
- **Smaller CUTLASS tiles.**
  - Measured: omat0-cutlass-tile was rejected on the A100 (1.012–1.017).
  - Reason: the warps per SM stay the same.
- **Skipping skin-shell edges.**
  - Reason: 373,760 edges is 74.75 per atom, the count inside 6 Å for SrTiO3's density (≈ 76), so the force
    call already sees only edges inside the cutoff.
