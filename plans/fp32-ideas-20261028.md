# Seven more float32 speed-up ideas: cheap checks (28 October 2026)

The owner asked for more creative float32 ideas after `plans/ideas-20261027.md` found no float32 lead left, then:
"Go ahead and try out all seven ideas with cheap checks first where possible". Branch `fastmace/fp32-ideas-20261028`
(from main `610e5c5c`). Every number is MH-1 r2SCAN, the default hybrid float32 plan, TF32 off, unless a row says
otherwise.

**Reference profile:** NbCl5 3×3×3 (1944 atoms), float32, local RTX 5060 Ti, main `aaeac537`
(`plans/ideas-20261027.md`, probe 2). The GPU span per MD step is 19.5 ms. Of the eager kernel time:
- atom GEMMs (cuBLAS plus `joined_products`): 9.0 ms;
- atom elementwise: 3.05 ms;
- symmetric contraction: 1.22 ms.

## Idea 7: linear layers to merge (CPU, float64, stock MACE)

`tools/bench/fp32_fold_check.py`: NaCl 2×2×2 with three Nb atoms, stock MH-1, float64 on the CPU. It folds
`products.0.linear` into its consumers (`interactions.1.linear_up`, `interactions.1.skip_tp`, `readouts.0.linear`)
and `products.1.linear` into `readouts.1.linear_1`:
- the first skip term `sc0` is the same for every atom of a species (spread 1.1e-15) and has no l=1 part;
- `interactions.1.skip_tp` ignores its l=1 inputs (those rows are exactly zero);
- folded against stock: energy equal to 1e-10 eV, forces within 1.3e-15 eV/Å (largest force 2.2 eV/Å).

**Then found:** FastMACE has done exactly this since OPT-T08 (`fastmace/rewrites/species/__init__.py`:
`fold_product_linear` with its `FoldedConsumer`, and `fold_readout_tail`), default on since OPT-DEF-2. The profile's
remaining `[5832, 512] × [512, 512]` and `[1944, 512] × [512, 512]` products belong to interaction 1's merged
`linear_1` + `linear_res` (`merged_residual`), which have a nonlinearity on both sides.

**No other chain is left:**
- `linear_res ∘ linear_up` (512 → 128 → 2048) would grow when folded;
- `linear_2` feeds the symmetric contraction, and the gate sits before it;
- the embeddings are species tables already.

## Idea 6: BF16x9 FP32 emulation

cuBLAS 12.9 and later can emulate FP32 GEMMs with BF16 tensor cores. NVIDIA reports 3–4× native FP32 on B200/H200
at M = N = K = 32768.

**Check:** `fp32_ideas_micro.py --mode emu`, eight atom-GEMM shapes. Each shape is captured in a CUDA graph and
timed, and its error is measured against float64. The plain process ran once, then one with
`CUBLAS_EMULATE_SINGLE_PRECISION=1 CUBLAS_EMULATION_STRATEGY=eager` (torch 2.14.1+cu130, cuBLAS 13).

| GPU (provider) | plain / emulated ms, [13608, 512] × [512, 512] | max error / (|A||B|), plain / emulated |
| --- | --- | --- |
| A100-SXM4-40GB (Colab) | 0.397 / 0.410 | 2.5e-7 / 2.9e-7 |
| RTX 5060 Ti (local) | 0.478 / 0.475 | see note |

All eight shapes agree within ±3 % on both GPUs, so cuBLAS does not apply the emulation there (the error
class is float32's own). This agrees with the reading that BF16x9 is a datacenter Blackwell (sm_100) path.

**Untested on datacenter Blackwell:**
- Colab refused the H100 and the RTX PRO 6000 (no entitlement), and its compute units are now 0.
- Modal's budget guard knows no B200 rate. October's remaining $2.7 also does not cover a B200 job's worst case.
- It would matter only if production moved to B200/B300; there the ceiling is the atom-GEMM share (37–50 % of the
  step).

**Note:** on the RTX 5060 Ti the error column came out exactly 0 for every shape, including Strassen's, so that
GPU's float64 reference of this script is not trustworthy (cause not investigated). The A100 errors stand.

## Idea 5: Strassen–Winograd

One level for `[rows, 512] × [512, 512]`: 7 products of 256-wide blocks instead of 8. The weight-side sums are
precomputed (the weights are fixed), which leaves 4 additions on the input side and 7 on the output side.

| rows | RTX 5060 Ti ratio | A100 ratio | A100 error, mm / Winograd |
| ---: | ---: | ---: | --- |
| 5832 | 1.89 | 2.07 | 2.6e-7 / 4.8e-7 |
| 9720 | 2.27 | 1.82 | 2.9e-7 / 3.3e-7 |
| 13608 | 2.42 | 1.77 | 2.6e-7 / 3.3e-7 |

At K = N = 512 the additions' memory traffic (about 230 MB for 13608 rows) costs far more than the eighth of the
multiplications they save (about 0.06 ms). Fusing them into a GEMM's prologue and epilogue would need our own GEMM,
which earlier rounds could not make beat cuBLAS. The ceiling is 12.5 % of the GEMM time minus the smaller tiles'
efficiency loss. **Falsified.**

## Idea 3: contraction fused into its GEMMs (on paper)

On NbCl5 the contraction reads the `[1944, 8192]` output of `linear_2` (64 MB) and writes `[1944, 2048]`. In the
backward the reverse happens.

**Ceiling:** fusing it into `joined_products` would save the write and re-read of the 64 MB tensor in the forward
(128 MB) and of its gradient in the backward (128 MB). That is about 0.6 ms at the measured 350 GB/s, 3 % of the
NbCl5 step, before any loss in the fused kernel.

**Cost:**
- It needs our own symmetric contraction (MH-1's correlation 3, cuEquivariance's kernel today) inside a GEMM whose
  tiles span all four l blocks of an atom block.
- Idea 1 attacks the same traffic generically.

**Dropped on paper,** by the same rule as F2 (`plans/ideas-20261027.md`): a ceiling of 3 % does not justify a
kernel.

## Idea 1: L2-sized atom blocks

The idea is to run an interaction's atom-level chain (GEMM, gate, GEMM, residual) on one atom chunk at a time, so
each chunk's intermediates stay in L2 instead of going through DRAM. `tools/bench/fp32_ideas_micro.py` on the local
RTX 5060 Ti (32 MB L2) and a Colab A100 (40 MB L2):

- **`bw`:** a copy runs at about 1.55-1.73 TB/s while it fits in L2 (up to 16 MB) and at about 350 GB/s from 24 MB.
- **`chain`** (six pointwise kernels over 61 MB, split into atom chunks): at 2/4/8/16 chunks the ratio is
  0.99/0.71/0.45/0.45 locally and 1.00/0.81/0.56/0.58 on the A100. Pointwise traffic gains as soon as a chunk fits
  in L2.
- **`gemmchunk`** (one `[rows, 512] x [512, 512]` product split into 2/4/8 launches), local ratios:
  - 1944 rows: 1.13/1.32/1.88;
  - 5832 rows: 1.07/1.16/1.40;
  - 9720 rows: 1.06/1.20/1.31;
  - 13608 rows: 0.96/1.11/1.17.
  On the A100 the penalties are 1.2-2.0. Smaller GEMMs lose efficiency, which works against the pointwise gain.
- **`block`** (both effects together: NbCl5's four l blocks, each run as GEMM, sigmoid times value, GEMM and
  residual): 3.25 ms whole. At 2/4/8/16 chunks the ratios are **0.868**/0.901/1.009/1.294.

**Limits of the check:**
- `block` runs the gate as eager kernels (sigmoid and multiply apart, each writing its result). Inductor fuses the
  gate and residual in the model, so the model writes less pointwise traffic than `block` does. The 13 % is
  therefore an upper bound for these four layers.
- `block` ran only locally. The A100 has `chain` and `gemmchunk` only; Ada has nothing (Colab compute units at 0,
  workstations full).

**Verdict: survives the cheap check.** The best split is 2 chunks; from 8 chunks on, the GEMM penalty eats the
gain. A general rule would size the chunks from the GPU's L2 (chunk bytes at most about half the L2) rather than
from a table per GPU or crystal. The next step would be a model prototype: split the atom rows of one interaction's
`linear_1` + gate + `linear_2` chain in the compiled forward and backward, then run an A/B on NbCl5 and NaNbO3 on
sm_120, Ada and A100. The ceiling is the atom-elementwise share (3.05 ms) times the pointwise saving, less the GEMM
loss, so at most about 1-1.5 ms (5-8 %) on NbCl5 and less on small cells.

## Idea 2: more pointwise recompute in the backward

`tools/bench/fp32_recompute_screen.py` turns off AOTAutograd's min-cut heuristics `ban_recompute_used_far_apart`,
`ban_recompute_long_fusible_chains` and `ban_recompute_materialized_backward` (`FP32_RECOMPUTE=far|chains|
materialized|all`). `ban_recompute_not_in_allowlist` stays on, so matrix products are never recomputed.

**Run:** `tools/step_breakdown.py` on the local RTX 5060 Ti, ABBA (`base` a1, `all` b1, `all` b2, `base` a2), with
the FX-graph and autograd caches off. Results are in `results/fp32-ideas-20261028/local-rtx5060ti/recompute/`.

| Crystal | Saved values, base / all | Saved MiB, base / all | Force graph ms, base a1/a2 | Force graph ms, all b1/b2 |
| --- | --- | --- | --- | --- |
| NbCl5 3x3x3 | 86 / 78 | 610.9 / 608.5 | 18.46 / 18.35 | 18.49 / 18.38 |
| NaNbO3 3x3x3 | 86 / 78 | 643.9 / 639.8 | 14.343 / 14.368 | 14.383 / 14.393 |

The partitioner recomputes 8 more values, but they are small; the big saved tensors are GEMM outputs, which the
allowlist protects. Only 2-4 MiB less is saved, and the step is 0.2 % slower (within noise, never faster).
**Falsified:** the default partitioner already recomputes the pointwise work that is worth recomputing.

## Idea 4: independent backward branches on a second stream

**Ceiling.** `tools/bench/fp32_critical_path.py` reads Inductor's generated wrapper code (`TORCH_COMPILE_DEBUG`,
NbCl5, base plan). It builds the launches' read/write dependency graph, times each launch from the same run's
kernel sequence, and computes the critical path (`results/.../critical_path_NbCl5.txt`):

| Graph | Kernel sum ms | Critical path ms | Off the path ms |
| --- | ---: | ---: | ---: |
| forward | 7.96 | 3.33 | 4.63 |
| backward | 12.15 | 9.83 | 2.32 |
| forward + backward | 20.11 | 13.48 | 6.63 |

Off the joint path: GEMM 4.72 ms, Triton pointwise 1.53 ms, cuEquivariance 0.20 ms, radial tables 0.17 ms. This
ceiling assumes concurrent kernels do not share the GPU.

**Overlap check.** `fp32_ideas_micro.py --mode streams` ran pairs of kernels on one stream and on two streams in
one CUDA graph (local RTX 5060 Ti). "Hidden" is the share of the shorter kernel's time that the second stream saved:

| Pair | ms, kernel 1 / kernel 2 | ms, one stream / two streams | Hidden |
| --- | --- | --- | ---: |
| GEMM 13608 rows + pointwise 64 MB | 0.483 / 0.339 | 0.825 / 0.802 | 7 % |
| GEMM 5832 rows + pointwise 64 MB | 0.233 / 0.354 | 0.566 / 0.555 | 5 % |
| GEMM 9720 rows + GEMM 13608 rows | 0.367 / 0.479 | 0.814 / 0.829 | -4 % |
| GEMM 1944 rows + GEMM 5832 rows | 0.091 / 0.232 | 0.319 / 0.338 | -21 % |

Each of these kernels fills the GPU (DRAM bandwidth or every SM), so a second stream has nothing idle to use, and
two GEMMs get slower. Applied to the 6.63 ms off the path, the overlap is at most about 0.1-0.3 ms (under 2 %) for
the GEMM-with-pointwise share and negative for the GEMM-with-GEMM share. The existing streaming-convolution side
stream gains only because its edge kernels are latency-bound. **Falsified** for the atom-level work.
