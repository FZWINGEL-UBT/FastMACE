## 2. Dual Horner in the w′ backward

**What the kernel does today** (`fastmace/kernels/oeq_streaming/wprime_backward.py:175-232`):
- **Per edge:** it computes the Chebyshev basis `cheb[6]` and, with `TABLE_W`, `dcheb[6]` (`T_k′ · scale`).
- **Per weight:** it loads 6 coefficients (3 float2) and forms `w = Σ cheb·g` and `w′ = Σ dcheb·g`, 11 FMAs.

So the idea does not save loads: `TABLE_W` already reads one 6-float row per weight and gets the slope from the same
row. Two things would change:
- **Registers.** The 12 basis values stay live through the whole channel and path loop; Horner needs only `t` and
  `scale`.
- **Arithmetic.** Dual Horner costs 10 FMAs per weight against 11, the same.

**Why it could matter.** The kernel runs at 96 registers with 128-thread blocks, which is 5 blocks or 20 warps per SM
(31 % occupancy, `ops.csv`). The next occupancy steps are 80 registers (6 blocks) and 64 (8 blocks). Capping the
factored kernel at 80 registers spilled 80–224 bytes and ran 1.243× slower (`docs/validation/omat0-tp-backward.md`
§5). If Horner frees about 10 registers, a cap of 80 might fit without spills. That is the real hypothesis, and on
the A100 the factored kernel is arithmetic-bound, where more warps help.

**Risks:**
- **Accuracy.** The power basis on [−1, 1] at degree 5 has coefficients up to about 16–20× the Chebyshev ones, so
  float32 cancellation grows. The table certificate (§6.1 of the SPEC) has to be re-run with the Horner evaluator in
  float32, and so do the force and stress gates. The NbCl5 stress is already over the limit on the A100 and
  accepted, so any loss there shows first.
- **Dependency chains.** Horner chains are serial, 5 FMAs long. Each lane works through many weights, though, so the
  compiler can interleave them.

**Screen:**
1. Render the kernel with a `HORNER` option. Convert G to the power basis in float64 at table build; the cutoff,
   lower clamp and slope scale stay unchanged.
2. Compare `ptxas` registers and spills.
3. Kernel lab on the A100 and the Ada: Horner, Horner with maxreg 80, and the base.
4. Only if that wins: run the certificate, the GPU test, the gate, and the MD A/B in both orders.

The ordinary radial-table kernels (Clenshaw, 0.42 ms forward and 0.32 ms backward per call) are memory-bound Triton
kernels. Horner there is a side branch with little to gain.

## 1. Dense CUTLASS species skip with a selected-store epilogue

**Profile check.** The figures match `ops.csv`:
- **Forward selection:** `triton_poi_fused_cat_index_mul_sum…` takes 135.3 µs.
- **Backward expansion:** four `…add_expand_mul_slice_slice_backward_t_tf32x3_mm…` kernels with input
  `[5000, 1, 3, 1]` take 57.9 + 38.1 + 21.5 + 7.6 = 125.1 µs.
- **Together:** 260 µs, 1.9 % of the call.

**Why this differs from what was rejected:**
- The grouped Triton species GEMM tied on the A100 (0.992 / 0.991), because Triton's 3×TF32 dot is about 3× slower
  per FLOP than CUTLASS.
- The gathered CUTLASS kernel tied too (0.993 / 0.992), losing to the per-call row order and indices
  (`results/omat0-kernel-lab-20261103/README.md` §11).
- This idea keeps the dense, ungathered product, which already wins, and removes only the tensors around it: the
  forward writes one species block in three, and the backward never materialises the 3×-wide zero-filled gradient.
  It does the same FLOPs.

**Ceiling.** The selection kernel's reads and the expansion's writes go, but some of those kernels also carry fused
adds and slice-backward work that would move elsewhere. A realistic gain is 1–1.5 % of the A100 step.

**Cost.** A CUTLASS epilogue visitor that stores row r's columns only for its species (a per-row predicate), and an
A-operand iterator for the backward that returns `onehot[r, s] · g[r, :]` without storing it. The cubin is prebuilt
(`fastmace/kernels/cutlass/`), so this means a cubin rebuild and new GPU tests.

**Screen.** Build only the forward epilogue first and time the four-irrep chain, the GEMMs plus selection, inside the
compiled step as the owner's list says, not as an eager GEMM. Build the backward iterator only if the forward wins.
This is A100-only: the RTX GPUs keep `SPECIES_GEMM`.

## 3. No redistribution tile in the tensor-core forward

**The current kernel** (`ops.csv`): 384 threads × 168 registers = 64,512 of 65,536 registers, and 151,040 bytes of
shared memory, so one block per SM. **Registers alone already allow only one block.** Removing the 72 KB tile does
not raise occupancy unless registers drop to about 85, which is not realistic for this kernel. The one gain would be
a schedule that the shared memory now forbids (ten paths per block, 265 → 130 KiB), and that schedule needs more
registers, not fewer.

**Earlier evidence:**
- `F-tc-no-redistribute`, which kept the reservation, gave 0.980 on the older kernel
  (`results/omat0-kernel-lab-20261103/a100-sxm4-tc-lab/summary.txt:15`).
- The launch screen found nothing from `W_TILE_REGISTERS` 80 (1.001) or `BLOCKS_PER_SM` (`omat0-launch-screen`).

**Verdict.** About 2 % of a 3.7 ms kernel, with no occupancy lever. Worth a timing-only bound (tile and accesses
removed, launch recomputed) only together with a schedule experiment that also cuts registers. Do not build the
register transpose before such a bound shows more than the old falsifier.

## 4. Path-streamed, fully tabulated forward

**The estimate.** A tabulated w costs 6 FMAs per weight against 65 for `a·W`, but it reads the coefficient row:
- **Coefficient traffic:** 1,280 × 6 × 4 B = 30 KB per edge, 11.5 GB per call.
- **Fit to the L2:** the value table is 164 MB, against the A100's 40 MB L2.
- **Time:** at 1.5–2 TB/s that is 6–7 ms, against today's whole 3.70 ms forward.
- **The product it replaces:** 373,760 × 1,280 × 65 × 2 = 62 GFLOP, about 1.2 ms on 3×TF32 tensor cores.

This is the same slab traffic that already bounds the w′ backward ("the remaining cost is the value-table slab",
`omat0-tp-backward.md` §5). Doing it twice per step moves the table read into the forward without removing it from
the backward.

**Earlier evidence.** The `NS-slab` bound (w from the slab in the forward) ran 1.30× the message-only forward on the
RTX 5060 Ti, with 96 bytes of spills (`results/omat0-kernel-lab-20261103/README.md:472`). The A100 was not measured.

**Verdict.** Do not build. If the owner wants the A100 answer, the existing `NS-slab` lab variant on the A100 at
degree 5 is one cheap Modal job (about $0.10) and settles it.

## 5. Euler identity for the density adjoint

The identity holds for homogeneous orders. But the budget it replaces is one 55.7 µs reduction
(`triton_red_fused_add_div_mul_neg_slice_slice_backward…`, `[5000, 2048]`), 0.4 % of the call. The degree-weighted
output `Σ ν P_ν` has to come from cuEquivariance's symmetric contraction, which we run unchanged (§3.7 of
`omat0-a100-optimisations.md`). A second contraction call, or rescaled path coefficients, costs about the
contraction's own 100 µs forward. Park it.

## Moments per piece (screened out by the list itself)

We agree. The tiled and MD runs are disordered, and 1.46–1.96× the accumulator size at 0.03–0.10 Å displacement
rules it out as a general optimisation (AGENTS.md: optimisations must work for any structure).

## The C1/C3 warning

The list warns that OMAT-0's first density block calls `skip_tp(message, node_attrs)` after geometry-dependent
processing, and that this must not be replaced by a constant species table. The generic fold
(`fastmace/generic-fold-product`) does not do that:
- **What it folds:** only `products.0.linear`, into interaction 1's `linear_up`, its `SpeciesSkip` (a per-species
  matrix applied to the features, not a table) and readout 0's linear.
- **The guard:** the generic path requires `species_skip`, not `species_tables`.
- **The check:** the CPU test matches the stock density model to 1e-10 relative in float64.
