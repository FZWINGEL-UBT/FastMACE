# OPT2-T01: the radial last layer fused into the streaming convolution

Plan: `plans/opt-2.md`, OPT2-T01 (owner, 21 October 2026: "Go ahead and try all 5 ideas as much as
possible"). Baseline: main `eb70cfd` with the OPT-T08 records on. Source of the ceiling: OPT-T09
(`docs/design/opt-T09-step-breakdown.md`) and ResearchModule's
`studies/symmetrix_xl/STREAMED_EDGES_RESULTS.md` (14 October 2026), cited below as "the October study".

## 1. What is to be removed

In MH-1's second interaction, the folded radial last layer produces the per-edge tensor-product weights
`w = a Wfᵀ`:
- `a` is `[E, 65]`: 64 hidden channels plus the folded cutoff column;
- `Wf` is `[1280, 65]`, 333 KB;
- so `w` is `[E, 1280]`: 10 paths × 128 channels.

The receiver-streaming convolution (OEq PR 223, vendored in `fastmace/kernels/oeq_streaming`) reads `w` in
the forward and writes its gradient `dw` in the backward. The Triton input gradient
(`fastmace::folded_linear_input_grad`) then reads `dw` to form `grad_a = dw Wf`.

`w` and `dw` are each written once and read once per force call: 42 MB each on NaCl, 288 MB on NbCl5 and
423 MB on NaNbO3. The four kernels involved, per force call (OPT-T09; ncu durations, used for ratios):

| | NaCl | NbCl5 | NaNbO3 |
| --- | ---: | ---: | ---: |
| Folded layer forward GEMM `a Wfᵀ` (writes `w`) | 174 µs | 1,288 µs | 1,991 µs |
| Streaming convolution forward (reads `w`) | 111 µs | 822 µs | 1,183 µs |
| Streaming convolution backward (reads `w`, writes `dw`) | 490 µs | 1,777 µs | 2,722 µs |
| Folded layer input gradient, Triton (reads `dw`) | 236 µs | 1,742 µs | 1,193 µs |
| **Sum** | **1.01 ms** | **5.63 ms** | **7.09 ms** |
| Share of ncu's force-call kernel time | 26 % | 24 % | 37 % |

**The October ceiling** was measured with a stub that ran OEq's shared-weight convolution, so no per-edge
weights were read or written. It gave 16.0 % of the step on NaNbO3, 9.1 % on NbCl5 and 11.4 % on NaCl, on the
14 October default. The streaming kernels adopted afterwards made the convolution itself faster. The
ceiling is now the four kernels above minus whatever a fused kernel costs.

## 2. Why the earlier attempts fell short

**Weight prologue in OEq's design** (option 4.2, measured):
- OEq computes one edge per warp, so each edge's `w[e, :]` would be its own 65 × 1280 matrix-vector product,
  re-reading all of `Wf` per edge.
- That was 2.9–4.2 ms on NaNbO3, against 1.5 ms for the GEMM, before any traffic was saved.

**An own fused Triton convolution** (option 4.3, built):
- The forward reached parity at best: 4.30 ms against about 4.3 ms compiled.
- Forward plus backward was slower: 16.6 against 12.1 ms on NaNbO3, 12.8 against 11.3 ms on NbCl5.

**Generating `w` inside the PR 223 forward** (not built; the October analysis):
- A thread owning (receiver, channel) needs 650 weight values: 10 paths × 65.
- That is too many for registers, and 333 KB of shared memory for all 128 channels.
- A path-by-path variant still executes about 7 G multiply-adds on NaNbO3 (≈ 1.5–2 ms).
- The backward needs `w` recomputed.

**The arithmetic, which nothing changes.** Generating `w` costs as many multiply-adds as the GEMM: E × 1280 ×
65, which is 6.9 GMAC on NaNbO3, 4.7 on NbCl5 and 0.68 on NaCl. The backward needs `w` again, for the
sender-feature and edge-feature gradients. It also needs `grad_a = dw Wf`, a second product of the same size.

So a fused forward does one GEMM's work, and a fused backward does two. The saving is purely the
traffic of `w` and `dw`: about 4 × 423 MB on NaNbO3. On this card that traffic costs about 1 ms per pass
(the October copy floor: `w → dw` took 2.42 ms).

## 3. What is different now, and a design that could reach the ceiling

What has changed since October:
1. **The convolution is ours.** The PR 223 kernels are vendored and generated by our own schedule
   (`fastmace/kernels/oeq_streaming`), so a fused kernel can keep their tested path code. The October
   Triton kernel had to rebuild the convolution itself, and lost there before the weights mattered.
2. **The edges are receiver-sorted CSR**, with the compacted count bound to the neighbour list. A block can
   own a run of receivers with a known edge range. That is the edge-tiling a reuse of `Wf` needs.
3. **The compute floor is known.** `w` generation at cuBLAS's measured FP32 rate (16.7 TFLOPS) costs about
   0.83 ms on NaNbO3. Today's forward GEMM takes 1.99 ms because it writes 423 MB (the October study: the
   write alone is 1.28 ms). So the GEMM does not bound the fused forward; arithmetic efficiency inside the
   convolution does.

**Forward design (receiver-owned, like PR 223):**
- **Block:** a run of R receivers × a slice of C channels, e.g. R = 8, C = 16: 128 threads, each owning
  (receiver, channel) as today.
- **Shared memory:**
  - `Wf` restricted to the block's channels: 65 × 10 × C floats, 41.6 KB for C = 16, loaded once per block;
  - the current edge chunk's `a` rows: T edges × 65 per receiver.
- **Per chunk of T edges of its receiver,** each thread:
  - computes `w[t, p] = Σ_k a[t, k] Wf[k, p, c]` for its channel, T × 10 values in registers;
  - reads each `Wf` value once per T edges, and `a` as a shared-memory broadcast;
  - then runs PR 223's unrolled path code with `w[t, p]` in place of the load from global memory.
- **Reuse of `Wf`:** R × (degree) edges per load, instead of one edge.
- **Shared-memory traffic:** about 3 loads per 8 multiply-adds at T = 8. That is about 0.9 ms of load
  issue on NaNbO3, against 0.6 ms of FMA issue: shared-memory bound, but below today's forward.
- **Estimate:** the folded GEMM plus convolution forward, 3.17 ms on NaNbO3, would become about 1.2–1.8 ms.

**Backward design (edge-tiled):**
- **Block:** a tile of T consecutive receiver-sorted edges × a channel slice, with `Wf` for the slice in shared
  memory.
- **Per tile:**
  - recompute `w` as in the forward;
  - form `dw[t, p, c]` in registers, as PR 223 does today;
  - use `w` for the sender-feature gradients (atomics, as today) and the edge-feature gradients (warp
    reduction, as today).
  - Then contract `dw` with `Wf` for `grad_a[t, k]`. Each thread's channel contributes a partial sum over
    its 10 paths. Partials are reduced across the slice's channels in shared memory, and across slices by
    atomics into `grad_a [E, 65]` (21 MB on NaNbO3, about 20 times smaller than `dw`).
- **Cost:** two GEMM-sized products (12–14 GFLOP on NaNbO3), the sender atomics (0.46 ms on NaNbO3, as
  today) and a read-only pass over `x`, `Y` and the output gradient.
- **Estimate:** 3.9 ms (convolution backward + folded input gradient) would become about 2.5–3.2 ms.

**Ceiling of this design:**

| | NaCl | NbCl5 | NaNbO3 |
| --- | --- | --- | --- |
| Optimistic | ≈ 0.35 ms (11 % of the step) | ≈ 2.3 ms (11 %) | ≈ 3.3 ms (18 %) |
| Realistic, if the in-kernel products reach 50–60 % of FMA peak | ≈ 0.2 ms (6 %) | ≈ 1.2 ms (6 %) | ≈ 2.0 ms (11 %) |

**Exactness:** `rounding`. The products are the same FP32 multiply-adds in a different order; there is
no TF32 and no lower precision (the October study: BF16 and FP16 storage of `w` fail the force criterion by
3–110×). The backward's `grad_a` atomics across channel slices make it non-deterministic. Either the record
declares `deterministic=False`, so the reproducible mode refuses it, or the slices write separate partials
that a small kernel sums in a fixed order. I plan the deterministic variant, costing 4 × 21 MB of extra
traffic on NaNbO3.

## 4. Risks

- **The October result:** an own fused kernel was slower. The differences here:
  - the path code is PR 223's, not a rebuilt convolution;
  - the reuse of `Wf` across a run of receivers is explicit;
  - nothing materialises.
  Whether CUDA C with register blocking reaches 50 % of FMA peak inside a gather-heavy kernel is unknown.
  That is the gate below.
- **Register pressure:** T × 10 weights plus PR 223's 40 output accumulators per thread. At T = 8 that is
  about 130 registers, so 25–33 % occupancy, like the GEMMs.
- **Shared memory:** 41.6 KB per block at C = 16 allows two blocks per SM, which is low.
- **Effort:** days, mostly the backward and its tests. The forward prototype comes first.

## 5. Plan and go/no-go

1. **Forward prototype (gate 1).** A standalone NVRTC benchmark (`tools/fused_conv_bench.py`) that renders
   PR 223's forward with the in-kernel weights, from our schedule for MH-1's second interaction. Inputs are
   real shapes: the receiver-sorted CSR of NaCl, NbCl5 and NaNbO3 3×3×3 rattled cells. Two checks:
   - **Correctness:** the message against `streaming_conv_forward(a @ Wfᵀ)`, within 1e-6 relative.
   - **Speed:** the fused forward against the folded GEMM + streaming forward, in a CUDA graph, local GPU.
   - **Go** if the fused forward saves at least 40 % of those two kernels on NaNbO3 and NbCl5, about
     1.2 ms and 0.8 ms.
   - **Stop** otherwise, recorded in `docs/rewrites.md`.
2. **Backward prototype (gate 2).** The same for the backward against the streaming backward + folded input
   gradient. Go if forward + backward together save at least 6 % of the step on NbCl5 and 10 % on NaNbO3.
3. **Record** `fused_radial_conv` (opt-in, `never_automatic`, requires `streaming_conv` and
   `fold_cutoff`), with:
   - its self-check against the unfused pair, values and input gradients;
   - CPU tests of the planner and the refusal path (the kernel itself needs CUDA);
   - the force gate on NaCl and NbCl5;
   - the local A/B in both orders, then murphy before Thursday 16:00 UTC if it is free.

## 6. Gate 1 result (21 October 2026): failed, stopped

`tools/fused_conv_bench.py` with `tools/fused_conv/fused_forward.cuh`, pinned copy `~/fastmace-runs/src-aed96b4`.
Setup:
- local RTX 5060 Ti (sm_120), local GPU reservation;
- MH-1's second-interaction problem: `ir_mul`, x 512, Y 16, weights 1280, message 5120, 128 channels;
- receiver-sorted ASE edges at r_max = 6 Å of the 3×3×3 cells, random float32 inputs;
- each variant captured in a CUDA graph, median of 50 replays.

Raw data: `results/opt2-T01-gate1-aed96b4/`.

| Structure (edges, mean degree) | folded GEMM + streaming forward | fused forward, best (CS 16, R 8, T 4) | saving | other configurations |
| --- | ---: | ---: | ---: | --- |
| NaCl (6,912; 32.0) | 229 µs (GEMM 168 + conv 101) | 251 µs | **−9.6 %** | T 2: −44 %; CS 8 / R 16: −58 %; CS 32 / R 4: −70 % |
| NbCl5 (51,084; 26.3) | 1,944 µs (1,133 + 801) | 1,857 µs | **+4.5 %** | −18 to −56 % |
| NaNbO3 (83,808; 77.6) | 3,045 µs (1,848 + 1,186) | 3,105 µs | **−2.0 %** | −32 to −54 % |

- **Correctness:** every configuration's message equals the reference bitwise. The kernel accumulates the 65
  products in the same order as cuBLAS's SIMT GEMM (one FMA chain over K), and the path code is the
  template's.
- **Speed:** the fused forward is at parity, from −10 % to +4.5 %. Gate 1 needed a 40 % saving on NbCl5 and
  NaNbO3. **Gate 1 fails, so the backward (gate 2) and the record were not built.**

**Why:**
- **Low FMA efficiency.** On NbCl5 the fused kernel performs the 4.7 GMAC of weight generation plus the
  convolution in 1.86 ms. The weight generation alone runs at about 18 % of FP32 FMA peak; cuBLAS's GEMM
  would need about 0.6 ms at its measured rate. The time saved by not writing and re-reading `w`
  (about 0.8 ms on NbCl5) is spent again on in-kernel arithmetic.
- **Shared-memory issue rate.** Each thread forms T × 10 weights per k from 10 `Wf` loads and T broadcast
  `a` loads, 14 loads per 40 FMAs at T = 4. That is above the 1:4 ratio this SM can issue.
- **Larger T** would reuse more but needs more registers. The thread already holds 40 message
  accumulators: 5120 outputs ÷ 128 channels.
- **Occupancy:** 128 registers and 37–87 KB of shared memory per block leave 1–2 blocks (4–8 warps) per SM.
- **The receiver-owned layout:** one thread per (receiver, channel) is what makes PR 223's forward
  atomic-free. It forbids the register-tiled GEMM micro-kernel (each thread a tile of edges × channels × slots)
  that reaching the GEMM's rate would need: the edges' contributions would then need a cross-thread
  reduction per receiver.
- **The backward** would do two such products in the same layout, so it could not do better than the
  forward.

This agrees with the October study's Triton result: parity for the forward, 4.30 against about 4.3 ms on
NaNbO3. Owning the PR 223 path code and the explicit `Wf` reuse did not change the outcome, because the
limit is the arithmetic layout, not the convolution code.

**Verdict:** rejected (conductor's rule: stop at a failed gate). The prototype and its bench stay on
`fastmace/opt2-T01` for the record; no library code was changed. A future attempt would need a different
decomposition, not more tuning. One example: a tensor-core-free register-tiled GEMM micro-kernel with a
deterministic per-receiver reduction. Its own design would have to show more than 40 % of the forward
before any build.
