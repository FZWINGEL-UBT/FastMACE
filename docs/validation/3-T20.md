## Item 1: species-change events against fixed species

### Method (`tools/bench/event_speed.py`)

- **Setup:** two `Simulation` sides in one process. MH-1 `matpes_r2scan`, hybrid float32, Langevin NVT,
  1 fs, friction 0.02/fs, 1500 K target, the same seed on both sides. NaCl and NbCl5 3×3×3.
  - **fixed:** `Workload(max_temperature_K=1500)`.
  - **events:** `Workload(max_temperature_K=1500, species_changes=True)`.
- **The event (host path):** after every 100 steps, `Simulation.update(species=…, momenta=…)` swaps the
  species of one atom of each species, with `exchange` momenta (the two atoms swap velocities with their
  species, §10.4), and does no energy evaluation. Its cost includes the force recompute and the canonical
  rebuild (conductor answer 2).
  - The pairs come from a seeded stream, the same in every run.
  - The species read and the momenta read use `Simulation.committed()`.
- **Timing:** each side advances with `run(100)`, so one timed unit is 100 steps plus, on the events side, one
  event.
  - 300 warm-up steps (3 events), then 12 blocks of 300 steps (3 events each), alternating through
    `fastmace.bench.ab.run_ab`.
  - Both orders: build order fixed-first with pattern ABAB, and events-first with ABBA.
- **Result:** the rate ratio median(fixed) / median(events). The run passes at ≥ 0.90.
- **Validity:** a run is invalid if anything compiled, any graph was captured
  (`engine.info()["recapture_log"]`) or another process used the GPU while timing.
- **Settling:** at 1500 K, new edge sizes keep appearing after 300 steps (the breakdown below saw 3 on NaCl).
  So after the 300 warm-up steps, the series keeps warming up untimed (`--settle 5`) until 5 chunks in a row
  add no graph capture on either side, for at most 3000 more steps. The record holds the settle steps.
- **Recorded per side:** skin, capacity headroom, edge-bucket fraction, edge bucket and capacity, and
  re-capture budget. Rule 11 (3-T05, merged) sizes these for the events side, which declares species changes;
  the fixed side keeps phase 1a's values. Also recorded: captures, neighbour rebuilds, canonical points, final
  temperature and potential energy, and species counts.
- **Rows:** the structure's species, and the superset {Na, Nb, O, Cl} on both sides (conductor answer 3).

### Smoke run (not the measurement)

Run `3-T20-smoke`, NaCl only, 100 warm-up steps, 2 blocks. Local PC (Fabi-PC, WSL2), RTX 5060 Ti,
`mace_cueq_oeq`, FastMACE b790704.

| Structure | fixed ms/step | events ms/step | rate fixed/events | Valid |
| --- | ---: | ---: | ---: | --- |
| NaCl | 2.928 | 3.308 | 0.885 | yes |

The two sides' plans are identical apart from the `workload.species_changes` line. Two blocks after a short
warm-up are not enough to judge. The breakdown below puts one event's cost at 15 ms, not the 38 ms this smoke
run implies.

### Breakdown of one event (`tools/bench/event_breakdown.py`)

Run `3-T20-breakdown-acd1615`: local PC, RTX 5060 Ti, `mace_cueq_oeq`, torch 2.14.1+cu130, FastMACE acd1615
(the JSON's `fastmace_commit` is null, because WSL's git cannot follow the worktree's `.git`; fixed in c5f3bcc).
The events side alone, warmed up for 300 steps with 3 events, then 10 rounds.

**Uninstrumented** (medians of 10):

| Structure | Atoms | MD step | Event | Event in steps | Chunk after − chunk before | Expected rate ratio |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| NaCl | 216 | 3.030 ms | 15.3 ms | 5.1 | −0.5 ms (noise) | 0.952 |
| NbCl5 | 1944 | 21.47 ms | 31.3 ms | 1.5 | 0.0 ms | 0.986 |

- "Expected rate ratio" is 100 steps / (100 steps + one event), from these medians.
- An event leaves no lasting penalty on the steps after it.
- Single events vary a lot. On NaCl the event took 14–31 ms, and the chunk differences ranged from −31 to
  +53 ms. Three new edge sizes were captured during the 10 rounds (8704 and 9216 edges as the 1500 K cell
  heats).
- On NbCl5, one capture (58,880 edges) added 197 ms to the first round.

**Instrumented:** each piece is timed between device synchronisations. Times are inclusive, in ms per event,
means of 10.

| Piece | NaCl | NbCl5 |
| --- | ---: | ---: |
| event (`committed` + `update` + pair choice) | 17.5 | 32.4 |
| `Simulation.committed()` (device → host copy) | 0.79 | 1.31 |
| `Simulation.update` | 16.6 | 31.0 |
| · `Transaction.quiesce` | 0.02 | 0.02 |
| · `Transaction.snapshot` (registry snapshot 0.79 / 0.99) | 0.96 | 1.15 |
| · `Transaction.apply` | 0.94 | 1.24 |
| · `Transaction.refresh` (derived buffers) | 0.56 | 0.62 |
| · `Transaction.resume` | 13.8 | 26.7 |
| · · `canonicalise(reevaluate=True)` | 13.7 | 26.7 |
| · · · `force_field.rebuild` (neighbour list) | 1.63 | 2.28 |
| · · · `force_field.compact` + edge-count host sync | 0.40 | 0.42 |
| · · · **`_force_stage` (force evaluation)** | **11.4** | **23.6** |
| · · · `integrator.start` | 0.01 | 0.01 |
| · · · rest (flags, flush) | 0.25 | 0.38 |
| · `update` rest (validation, host arrays) | 0.38 | 1.22 |

**Where the time goes:**
- The force evaluation at the canonical point dominates: 65 % of the event on NaCl and 73 % on NbCl5.
- `GraphEngine._force_stage` calls the force field directly. It does **not** replay the captured force graph.
  - On NaCl it costs 3.8 MD steps (11.4 ms against a 3.03 ms step).
  - On NbCl5 it costs 1.1 steps (23.6 against 21.5 ms), where the call is GPU-bound and the launch overhead
    matters little.
- Next come the neighbour rebuild (1.6–2.3 ms), the snapshot (about 1 ms) and the apply (about 1 ms).
- If a canonical point replayed the captured force graph of the current edge size (one step's force part,
  about 3 ms on NaCl), a NaCl event would cost about 7 ms. The expected ratio would then be about 0.98.

## Item 3: float32 ΔE errors against float64 (from 3-T11)

Source: `docs/validation/3-T11.md`, "Acceptance item 3", and the result files
`results/3-T11-rtx5060ti-20261022/<model>-<structure>/metadata.json`.
- **Setup:** local PC, RTX 5060 Ti, `mace_cueq_oeq`, FastMACE 57d788f, cc57ebc and e5b988f (the measured
  paths are the same in all three). Hybrid float32 graph plan, MC workload over the superset
  {Na, Nb, O, Cl}, rule 11. `tools/validation/move_energy_precision.py`.
- **Snapshots:** after 2000 steps of 1 fs at 300 K, and after 2000 more at 1500 K.
- **Samples:** 4 swaps per superset pair, 2 atoms of each present species transmuted to every other superset
  species, and 8 displacements of 0.15 Å.
- **Reference:** the gate's float64 reference. **Production:** the engine's float32 MC evaluator, which is the
  captured energy-only graph.
- **Values:** the worst |ΔE₃₂ − ΔE_ref| per move type, in k_B·T_min with T_min = 250 K. The gate's limit is
  0.01.

| Model | Structure (atoms) | T (K) | Swap | Transmute | Displace |
| --- | --- | ---: | ---: | ---: | ---: |
| MH-1 `matpes_r2scan` | NaCl (216) | 300 | 0.00037 | 0.00036 | 0.00032 |
| | | 1500 | 0.00039 | 0.00026 | 0.00018 |
| | NbCl5 (1944) | 300 | 0.0011 | 0.00035 | 0.00074 |
| | | 1500 | 0.0019 | 0.00049 | 0.00050 |
| | NaNbO3 (1080) | 300 | 0.0024 | 0.0029 | 0.0015 |
| | | 1500 | 0.0035 | 0.00081 | 0.0011 |
| MH-1 `omol` (all-electron E0) | NaCl (216) | 300 | 0.00046 | 0.00029 | 0.00028 |
| | | 1500 | 0.00053 | 0.00030 | 0.00029 |
| | NbCl5 (1944) | 300 | 0.0011 | 0.00070 | 0.00068 |
| | | 1500 | 0.00057 | 0.00040 | 0.0011 |
| | NaNbO3 (1080) | 300 | 0.0014 | 0.0012 | 0.00069 |
| | | 1500 | 0.0024 | 0.0013 | 0.00058 |

- **Every case passes the gate.** The worst is 0.0035 k_B·T_min (76 µeV), on NaNbO3 swaps at 1500 K: a margin
  of about 3. The gate would fail float32 there for T_min below about 90 K.
- **The float64 copy** errs by at most 2 × 10⁻⁶ k_B·T_min.
- **What `mc_energy_precision="auto"` picks:** float32 (the force precision) for these models and structures
  at T_min ≥ 250 K. The gate decides per run (decision 35).
- **OMOL-0 XL is not measured.** Its float64 references did not finish locally or on a Modal A100 ($2.22,
  3-T11). Its move-energy gate is far slower than §12.3's "seconds to a minute" (3-T11 open finding 4).
- **The L4 repeat of item 3** reruns MH-1 `matpes_r2scan` on the three structures inside the T20 Modal job
  (pending).
