# 6-T16: CPU suite scheduling

Owner request: reduce the roughly 35-minute CPU suite before publishing 1.0.
**Result: 4,655 passed, 553 skipped in 831.34 s (13 min 51 s), versus 1,998.13 s (33 min 18 s)
for the previous complete release suite: about 2.4× faster, 58% less elapsed time.**

## Change

Use `--dist=load --maxschedchunk=1` in the documented CPU commands, the phase-6 CPU runner and the
manual hosted CPU workflow. Keep eight local workers, `OMP_NUM_THREADS=2`, both test directories,
and every test, sample count, trajectory length, seed, tolerance and assertion unchanged.
No `fastmace/` or `tests/` file changed.

With 5,199 collected items and eight workers, pytest-xdist 3.8.0's default load scheduler initially queues
162 consecutive items per worker (`5199 // 8 // 4`). The 18 MC enumeration/statistics cases consumed
1,669 s of combined test elapsed time in the previous run and could remain queued on one worker.
All cases combined took about 5,092 s, so the 1,998 s wall time exposed a long scheduling tail.
Small chunks let the scheduler distribute those expensive cases rather than reserving a large block.
The measured run assigned the 18 MC cases across all eight workers (1–3 cases per worker).

## Full-suite verification

```bash
CUDA_VISIBLE_DEVICES='' OMP_NUM_THREADS=2 PYTHONDONTWRITEBYTECODE=1 \
  ~/environments/fastmace_cpu/bin/python -m pytest \
  -n 8 --dist=load --maxschedchunk=1 tests/cpu tests/gpu
```

Machine: Intel Core Ultra 7 270K Plus, 24 cores; WSL2 Ubuntu with 40 GB RAM. Environment:
`~/environments/fastmace_cpu`, torch 2.14.1+cpu, pytest 9.1.1, pytest-xdist 3.8.0.
Run from a freeze archive of main `68a159f3894c5701422bf95db17438be0e65a242`, with
`FASTMACE_BASELINE=~/fastmace-baseline/1a-T18`, one local suite, no local GPU workload.
A temporary controller-only profiling plugin recorded worker IDs and durations; it changed no tests.

| | Previous complete release run | Small chunks |
| --- | ---: | ---: |
| Pytest elapsed | 1,998.13 s | 831.34 s |
| Passed | 4,646 | 4,655 |
| Skipped | 553 | 553 |
| Failed/errors | 0 | 0 |
| Collected | 5,199 | 5,208 |

The old and new `fastmace/` trees are identical (`1dc1074bf7bad1d0eee6c0f24ef28337b86aee2e`).
JUnit comparison found **zero missing prior cases** and **zero previous passes newly skipped**.
The only nine added cases are `test_oeq_wheel_support.py`'s Python-version metadata tests (6-T15).
The newly started default-scheduler release run was intentionally stopped before completion; it is not
counted as passing evidence. The complete prior release run supplies the baseline.

Records: `results/6-T16-cpu-scheduling-20261025/{summary.json,junit.xml,suite.log}`.
The JSON's wall times come from JUnit (1,998.114 s and 829.651 s); pytest's console includes about
1.7 s more startup/shutdown in the new run. Both give approximately 2.4× and 58% reduction.

## Limits

This is an observed before/after comparison on the same machine and environment, not a controlled
alternating A/B timing experiment. Cache state and fixture placement may affect exact timings on other
machines. The worker limit and numerical threading stay unchanged; no production CPU/GPU speed claim
follows from this test-runner improvement. Hosted CI remains manual-only as the owner decided.
