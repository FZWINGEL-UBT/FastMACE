# 2-T21d: `fm.Simulation` dropped edges from the forces after 0.2 ps

21 October 2026. Branch `fastmace/2-T21d` (5bc12e9, f6a2e86) on main a389165.

## Defect

2-T23 saw in-process and subprocess-runner `fm.Simulation` runs (MH-1 hybrid FP32, NaCl 3×3×3 from
0 K, 300 K) heat far above their target from about 0.2 ps on: 897 K at 0.5 fs, NaN at 2 fs. The
planner's engine stepped directly (`tools/trajectory_versions.py`) stayed smooth.

**Cause.** `GraphEngine.prepare()` (2-T15b, b5796b3, merged into main as d14be8c on 20 October 2026,
13:05 CEST) captures the first step's stages before it. It captured B (and, speculative, ACB) without
first calling `force_field.use_edges(edges)`, which the step always does before running B. A CUDA graph
records the edge views it reads, so the graph keyed by the padded initial edge count (7168) kept the
build's exact views (6912 edges, `graph.py`: `force_field.use_edges(initial_edges)`). As the atoms move,
the compacted edge count grows inside the padded bucket (6912 → about 7070), so nothing triggers a redo
or a recapture, and the replayed B graph never sees the new edges: non-conservative forces and heating.
The lazy capture of 1b sets the views first, so the direct-engine path was right. On the CPU nothing is
captured, so no CPU test could see it.

**Affected:** every `fm.Simulation` run with CUDA graph capture on, in-process or in subprocess-runner
children (`fm.md` too, and ResearchModule's `main.py --engine fastmace --fastmace-api simulation`), on
FastMACE from d14be8c to this fix, from the step its edge count first exceeds the build's. Not affected:
direct planner-engine runs (`tools/ab_fastmace.py`, `tools/trajectory_versions.py`, ResearchModule's
`--fastmace-api adapter`), CPU runs, eager and reference tiers, single evaluations (the gate).

**Fix.**
- `engine/graph.py`: `prepare()` sets each B/ACB key's edge views before capturing it, as
  `_step_checked`, `_step_pipelined` and `_step_speculative` do (AC, ACP and C read no edge views; NPT,
  stress and the strain path run inside B, and the fallback's candidates go through the same
  `prepare()`).
- A guard in `GraphEngine._captured` refuses any B/ACB capture whose active edge views differ from
  the key's count, for `prepare()` and the lazy capture alike.

## Two traps met on the way

1. **My bisect copies ran on the eager tier.** Copies of 2-T23's constructor did not reproduce, and
   recorded exact (unpadded) edge sizes. Their plans were revision 1, `fallback: mode eager: eager
   passes the reduced gate: the fault is in capture or compilation (BackendCompilerFailed:
   backend='inductor' raised:)`. The cause was my script's file name: `bisect.py` in the script's
   directory shadows the standard library's `bisect` for Inductor's compile workers, whose pool died
   ("SubprocPool unclean exit", then "Attempting to use a closed pool"). Renamed, the same constructor
   plans the graph tier at revision 0. Nothing in FastMACE chose eager wrongly, and the fallback is
   recorded, but two things are easy to miss:
   - the fallback reason ends at `BackendCompilerFailed: backend='inductor' raised:` and drops the
     underlying error, here `RuntimeError: Attempting to use a closed pool` (proposed follow-up: put
     the innermost cause of a chained compile error in the reason and the report line);
   - a run that falls back to eager is slower and steps differently (no capture, unpadded edges), and
     only `sim.plan.reason`, the report's plan line and `metadata.json` say so.
2. **A monkeypatched `GraphEngine.prepare` did not take effect** in my first lazy/old/new check and in
   a `PROBE_LAZY` variant of 2-T23's driver: ACP and B were captured before the first step anyway, so
   all variants ran the tree's own `prepare()` and showed no difference. Not resolved; the valid
   comparison is the library swap above.
