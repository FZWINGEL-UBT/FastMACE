# 4-T13: the subprocess runner's child aborts at exit

Found during the phase 4 acceptance preparation (plan task 4-T13), 23 October 2026. The fix was approved by the
conductor and is on branch `fastmace/4-T13-runner-abort`, so that it merges before the phase 4 freeze.

## The flake

`tests/cpu/test_subprocess_runner.py::test_mc_attaches_keeps_and_detaches_through_the_runner[fresh-children]`
failed once in 4-T10's trial merge under `-n 8`. The child had written an `ok` result and was then killed by
SIGABRT with "terminate called without an active exception". It passed 3 of 3 alone. The parent fails such a
call, correctly: `_launch` accepts a result only with exit code 0 (or `None`), no stop and status `ok`, and
otherwise raises `SubprocessRunnerError` ("killed by signal 6").

## Cause

`fastmace/engine/subprocess.py`, `_Heartbeat`: a daemon thread whose loop calls `write()` -> `text()` ->
`int(engine.state.step)`, a torch call that releases the GIL inside C++. `main()`'s `finally` called
`heartbeat.stop()`, which set the event but did not join the thread. The fresh child then returned from `main()`
and the interpreter finalised. If the heartbeat thread was inside that torch call at that moment, CPython 3.10
ended it with `pthread_exit` when it tried to take the GIL back; glibc's forced unwind ran through the noexcept
GIL re-acquire in torch's bindings, and that calls `std::terminate`. The window is the length of one `int(step)`
after `stop()`, so it showed only under load.

## Evidence

WSL2, `~/environments/fastmace_cpu`: Python 3.10.12, torch 2.14.1+cpu; scratch scripts, then the regression test.

| Script | Aborted (exit 134, the same message) |
| --- | --- |
| a daemon thread looping `int(tensor)`, main exits | 40 of 40 |
| the same, the thread stopped by an event and joined first | 0 of 40 |
| the real `_Heartbeat`, `start(1e-6)`, `stop()` as it was, then exit | 0 of 30 (window too narrow) |
| the real `_Heartbeat` with `text()` held in a larger torch call (the window widened), `stop()` as it was | 29 of 30 |
| the same, `stop()` then a join | 0 of 30 |

## Fix

- `_Heartbeat.stop()` sets the event and then joins the thread, if it was started, with a timeout of
  `PARENT_CHECK_S` (1 s). The loop's wait returns at once when the event is set, so the join waits for at most the
  write in flight.
- `main()`'s `finally` sets `heartbeat.simulation = None` before `stop()`, so no last write reads the engine.
- The parent-death path (`os._exit(3)` inside the loop) and the parent's check of the exit code are unchanged.

## Tests

- `test_stop_waits_for_the_heartbeat_thread`: a never-started heartbeat stops; a started one's thread is not alive
  after `stop()`.
- `test_a_child_exits_cleanly_while_its_heartbeat_is_inside_torch` (slow, about 40 s): 20 fresh interpreters, each
  with the widened window and `stop()`, all exit 0. Both failed before the fix and pass after it.
- Targeted, `fastmace_cpu`, `-n 2`: `tests/cpu/test_subprocess_runner.py` 22 passed (the new slow test included);
  `test_subprocess_worker.py`, `test_reproducible.py`, `test_contracts_2.py`, `test_simulation_options.py` 105
  passed. Ruff clean.
