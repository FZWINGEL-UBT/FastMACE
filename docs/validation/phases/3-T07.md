# 3-T07: energy-only graph and the MC evaluator

Plan task 3-T07 (`plans/phase-3.md`), 22 October 2026. Spec: §8.1 "Energy-only graph", §10.4
"Evaluation", "Baseline energy", "Energy precision", "Cost", and §7.3.

## What exists now

- **`MACEForceField.energy_only(positions)`.** A forward pass under `torch.no_grad()` with forces,
  stress and `training` off. It produces the force path's float64 sum and no `grad_fn`.
  - A compiled model compiles this call as one more variant, because grad mode and `training` are
    guarded (conductor answer 2).
- **`MACEForceField.follow(leader)`.** The float64 MC copy reads the float32 force field's compacted
  edges and unit shifts, and rebuilds the shifts in float64 from the float64 cell. It shares the
  leader's species, charge and total-charge sources.
- **`GraphEngine.energy(*, precision=None)`.** The energy-only graph, with key
  `("E", precision, edges)`.
  - It is captured on CUDA. On the CPU and in the compiled and eager tiers it runs directly.
  - It flags an edge overflow in 3-T04's word.
  - `add_energy_field` registers the copy, whose derived buffers join `GraphEngine.derived` as
    `energy.<precision>.*`, so 3-T03's transactions refresh them.
  - `energy_stage` gives the same evaluation as a plain function, for 3-T09's attempt graph.
- **`fastmace/mc/evaluator.py`.**
  - `MCEvaluator`: `evaluate`, `stage`, `baseline`, `accept`, `reject`, `current`, `tag` and `info`.
  - `EnergyCache`, tagged `(evaluator, precision, GraphEngine.state_version)`.
  - `float64_model(force_field, plan, backend=None)` and `float64_copy(...)`. The copy is eager (no
    `torch.compile`) and captured.
- **`tools/bench/mc_cost.py`.** The energy-only rows. T09, T10 and T20 add their sides.

The names are in `docs/design/contracts-3.md` ("Energy-only evaluation and the MC evaluator") and
pinned in `tests/cpu/test_contracts_3.py`.

## Cost: energy-only evaluation as a fraction of one MD step

- **Setup:**
  - local PC, NVIDIA GeForce RTX 5060 Ti, WSL;
  - `~/environments/mace_cueq_oeq` (in-process OEq runtime);
  - MH-1 `mh1-r2scan` (`~/models/mace-mh-1.model`);
  - plan backend hybrid float32, default MD plan (`MinimalPlanner`, 300 K);
  - structures from the 1a-T18 baseline export, 3×3×3.
- **Commit:** FastMACE 4e88f07 (branch `fastmace/3-T07`). The tool's own `fastmace_commit` field is
  empty, because WSL git cannot read a Windows worktree's `.git` file.
- **Protocol:**
  - in one process, MD steps and energy evaluations (`MCEvaluator.evaluate()`, the captured E
    graph) alternate in timed blocks;
  - the order rotates every round and is mirrored every second cycle;
  - 12 rounds, with blocks of 100 (NaCl) or 50 (NbCl5);
  - ratios are per round, and the median is shown.
- **Machine:** not quiet for NaCl. Other workers' CPU suites ran beside it, so its block spread was
  10–21 %. NbCl5's spread was about 1 %.

## Findings

1. **Energy-only float32 costs 0.42–0.44 of an MD step.** That is about twice the 22 % that §10.4's
   example needs for 90 % MD throughput at 50 attempts per 100 steps. Only §10.4 "Cost" reports
   it, as the spec says: there is no pass mark. A local-energy variant is the 1.x optimisation
   named there.
2. **A float64 evaluation costs 11–13 MD steps on the RTX 5060 Ti** (FP64 is slow on consumer GPUs).
   The hybrid float64 copy is 4 % faster than the cuEq one on NbCl5, so the plan's backend is the
   default copy backend, as conductor answer 1 has it.
3. **MACE's loader sets torch's process-wide default dtype.** Loading the float64 checkpoint into a
   float32 process left it at float64, and the float32 model's next Inductor recompile (a new edge
   bucket during MD) failed with "double != float".
   - Fixed: `float64_model` restores the default dtype, and the copy's forward runs under its own
     dtype.
   - Other places that load a second precision in one process (the gate's references, 3-T11) may
     need the same care.
4. **`GraphEngine.flag_edge_overflow(count, edges)` with a Python int `edges` could not be
   captured.** `torch.as_tensor(int, device=cuda)` is a host-to-device copy. It now compares a host
   limit as a scalar (fixed here; 3-T09 and 3-T10 use it inside their graphs).
5. **Compiled CPU forces vary between calls by about 1e-18,** independent of the energy-only path.
   Eager CPU is bitwise.
