## What changed

- `fastmace/simulation.py`: `_advance` catches decision 54's triggers raised by a step during `run()`
  (`fallback.mid_run_stage`: a capture error the graph engine tagged at a re-capture, or a Dynamo or Inductor
  compile error of the compiled tier). `_mid_run_fallback` then:
  - goes back to `_last_point` (5-T07's in-memory canonical point: the last restart write, else the setup's or
    the resume's state; the resume's point now carries the restart's output chunk indices);
  - runs the §9.4 search (`fallback.Fallback`) on the committed structure, with the gate's references and the
    MC move-energy references recomputed there (conductor's answer Q6);
  - gives the validated revision the point's state through 5-T07's `_restore`, rewinds the schedule, reopens
    `ChunkedOutput` with `resume_from` (chunks after the point deleted, never rewritten; from the setup state
    every chunk goes and row 0 is written again), and redoes the steps since the point;
  - records a report warning and a `fastmace.planner` log line, and excludes the search from the step time.
- Under `fallback="refuse"` the error is raised as it is, with `error.fastmace_mid_run` (failed step, point,
  stage, revision) and a note; nothing is written, so the last restart file stays resumable.
- One fallback per canonical interval (decision 54, conductor's answer): a second trigger before the next
  restart write raises `FallbackExhausted` with `fallback-mid-run-limit`, chained to the error.
- `fastmace/planner/fallback.py`: `candidate(step=, note=)` and `Fallback(step=, note=)` make every candidate
  revision at the point's step with the mid-run note in its reason; `mid_run_stage`, `mid_run_note`,
  `is_mid_run`, `mid_run_fallbacks` (read from the plan chain, so a resume keeps them), `mid_run_revision`
  (the decision `fallback.mid_run`, rule 14, `fallback-mid-run`), `mid_run_limit`, `mid_run_runner`.
- `fastmace/planner/rules.py`: rule 14's codes `fallback-mid-run`, `fallback-mid-run-limit`.
- `fastmace/provenance.py`: `counters.fallbacks` (`FALLBACK_KEYS`: step, from, to, reason, revision), within
  metadata minor 1 (as 5-T06's `segments`); `docs/design/metadata-schema.md`, `docs/design/planner-5.md`.

A mid-run fallback is not a tier switch: it is not in `counters.tier_switches` and does not count against
decision 53's limit (conductor's answer Q4). After a fallback off the graph tier, adaptation does not switch
again (one way, graph → compiled).

## Follow-ups

1. **Must fix before 5-T11's acceptance (conductor, 24 October 2026): MC streams across a fallback.** When the
   move set was attached after the point (a `run(mc=...)` call that started after the last restart write),
   the point has no MC record. The fallback re-attaches the move set, but its random streams, counters and
   cycle position continue from the failed run's state at the failure, not from the point. The redone steps
   then draw other MC random numbers than an uninterrupted run would, and the MC counters include attempts that
   were undone. Production swap MC (one `run(mc=...)` per segment) hits this whenever a failure comes before
   the segment's first restart write. A point with an attached move set restores the MC state from its record
   and is not affected.
2. A candidate that runs in a subprocess child (§9.4 step 3, a backend change after a compiled hybrid model)
   stops the run (`FallbackExhausted`, `fallback-mid-run-limit`, `fallback.mid_run_runner`) instead of being
   handed over to the subprocess runner mid-run (conductor's answer Q3).
3. A failure inside a subprocess runner's child is handled by the parent as before 5-T08 (Q3).
4. Errors raised inside an MC block's own evaluations (the MC evaluator's captures) are not triggers: only
   `engine.step()` is watched, and the fallback is refused inside an MC block.
5. Sinks registered with `add_sink` see the redone steps again (their snapshots after the point are dropped
   with the output queue, then queued again as the steps are redone).
